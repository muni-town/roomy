# TODO — Desktop (Tauri) HappyView session support

**Created:** 2026-09-29 · **HEAD:** 0d27f248 (HappyView session-swap diff, uncommitted)

## Why this is pending

The OAuth session swap in `packages/sdk/src/browser/oauth.ts` deliberately ships
**web-only**: when `window.__TAURI__` is present, `createOAuthClient` ignores the
HappyView env and keeps the tested legacy direct-PDS flow (`@atproto
oauth-client-browser`, IndexedDB sessions). Desktop users keep ~2-week public
tokens; web users get HappyView-custodied ~2-year confidential tokens.

## What is already in place (untested on desktop)

- `tauriLogin()` in `packages/sdk/src/browser/oauth.ts` already contains a
  HappyView branch: `client.prepareLogin(handle, {scope})` →
  `tauri.opener.openUrl(authorizationUrl)` → wait for the
  `space.roomy:/?state=…&code=…` deep link → `client.initCallback(search)`.
  It has never been run against a real PDS/HappyView instance.
- `build-prod.sh` writes both `oauth-client-metadata.json` (web) and
  `oauth-client-native.json` (desktop) at roomy.space.

## To ship HappyView for desktop

1. **SDK:** relax the Tauri force-legacy guard in `createOAuthClient` — let
   desktop opt in when `happyviewEndpoint`/`clientKey` are set (the gate was
   added as a safety rail; keep the half-config throw in both cases).
2. **Metadata (`packages/app-lite/scripts/build-prod.sh`):** decide the native
   doc's auth method. Until now it is hardcoded `token_endpoint_auth_method:
   "none"` so the *legacy* desktop client keeps working. Once desktop uses
   HappyView, apply the same confidential treatment as the web doc
   (`private_key_jwt` + `jwks_uri` when `HAPPYVIEW_JWKS_URI` is set) for ~2-year
   sessions — or defer if desktop should stay public-token.
3. **HappyView instance:** provision an auth key for the native client id
   (`https://roomy.space/oauth-client-native.json`) via
   `POST /admin/api-clients/{id}/auth-key`, and ensure the API client (hvc key)
   is registered with redirect `space.roomy:/`.
4. **Desktop build env:** bake `VITE_HAPPYVIEW_ENDPOINT` +
   `VITE_HAPPYVIEW_CLIENT_KEY` into `release-tauri.yml` (mobile desktop too).
   Note desktop bundles must land at the same time the web doc flips, since
   both docs are generated by the same build.
5. **Test matrix before enabling in CI:**
   - Local desktop build (`tauri dev`) sign-in: consent screen → deep link
     resolves → agent routes XRPC through the HappyView instance
     (`x-client-key` header, DPoP proof).
   - App restart restores the session from localStorage (`happyview:session:*`).
   - Sign out deletes the instance session and revokes at the PDS.
   - iOS/Android deep-link handling (separate handler paths from desktop).
6. **Rollout order:** web HappyView first, desktop only after its test matrix
   passes — never flip the JWKS/native-doc env while legacy desktop is still
   the shipping flow (it would break desktop login at the AS).
